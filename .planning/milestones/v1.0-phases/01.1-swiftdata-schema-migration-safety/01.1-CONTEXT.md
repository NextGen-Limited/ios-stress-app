# Phase 01.1 Context — SwiftData Schema Migration Safety

## Crash Signature

```
StressMonitor/StressMonitorApp.swift:82
Fatal error: Could not create ModelContainer:
SwiftDataError(_error: SwiftData.SwiftDataError._Error.loadIssueModelContainer, _explanation: nil)
```

Fires at app launch when `ModelContainer(for: schema, migrationPlan: AppMigrationPlan.self, configurations: [modelConfiguration])` throws. The `catch` block calls `fatalError`, permanently bricking the app for any affected device.

## Root Cause (verified)

**Migration plan reuses live `@Model` types across V1/V2** (`StressMonitorApp.swift:31-53`). Both `AppSchemaV1.models` and `AppSchemaV2.models` reference the same live class objects (`StressMeasurement.self`, `CharacterUnlock.self`), differing only by the appended `Habit.self`. SwiftData computes the migration diff by comparing V1's declared schema to V2's — because both point to the identical current class metadata, the diff for the two shared models is always empty. The plan encodes "V1 = current source shape," which is false for any device whose on-disk store was created by an older build.

When `ModelContainer(for:migrationPlan:)` runs:
1. Opens the existing `.store`, reads its persisted schema hash.
2. Compares on-disk schema against `AppSchemaV1`'s declared schema.
3. On-disk schema (created by a prior build before multi-factor fields, before `#Unique`, before `confidences`) does not match V1's claimed schema — because V1 is actually the current source, not the historical shape.
4. Looks for a migration stage from the store's real version → V2. None exists for the drift. The lightweight stage only knows "add Habit."
5. → throws `SwiftDataError.loadIssueModelContainer` → caught → `fatalError`.

## Compounding Issues (from swiftdata-auditor, 12 findings total)

### CRITICAL (launch-crash compound)
1. **Non-optional `StressMeasurement` fields lack property-level defaults** (`StressMeasurement.swift:10,11,23,25`): `restingHeartRate`, `categoryRawValue`, `isSynced`, `deviceID` have init defaults but no property-level defaults → not lightweight-migratable.
2. **`#Unique<CharacterUnlock>` not captured by any migration stage** (`CharacterUnlock.swift:10`): unique constraint drift; adding UNIQUE index to a column with existing duplicates is rejected by SQLite.
3. **`fatalError` on container creation with no recovery path** (`StressMonitorApp.swift:82`): any migration defect kills the app instantly on every launch, permanently, no way to recover without reinstall.

### HIGH
4. **CloudKit config inconsistency**: entitlements declare `iCloud.stress.ai.com`; active SwiftData `ModelConfiguration` has no `cloudKitContainer:` binding; orphaned `StressMonitorSchema.swift` references a *third* ID `iCloud.com.stressmonitor.app`.
5. **`StressRepository.mergeRemoteMeasurement` O(n) fetch-all-then-filter** (`StressRepository.swift:382-418`): fetches every `StressMeasurement` row per merge, filters in Swift. UI freeze at scale.

### MEDIUM
6. **`try? context.save()` swallows errors at 4 sites**: `StressMonitorApp.swift:159`, `CharacterCollectionViewModel.swift:78,104`, `HabitViewModel.swift:75`.
7. **`saveBatch` inserts all rows then saves once — no chunking** (`StressRepository.swift:65-81`).
8. **`HabitViewModel.loadToday()` saves unconditionally on every load** (`HabitViewModel.swift:48-72`).

### LOW
9. **Orphaned duplicate `StressMeasurement` definition at repo root** (`StressMonitor/Models/StressMeasurement.swift`): NOT compiled (iOS target's synchronized root is `StressMonitor/StressMonitor/`). Maintenance trap.
10. **`PhoneConnectivityManager` stores/uses main `ModelContext` from delegate callbacks** — currently safe (WCSession delivers on main queue) but implicit.

## On-Disk Store Verification

Inspected `default.store` on simulator `BC6D2019` (iPhone Air):
- Store already at V2 schema (`ZHABIT` table exists, 18 rows; `ZCHARACTERUNLOCK` unique index present, 5 rows; `ZSTRESSMEASUREMENT` 0 rows).
- `Z_CharacterUnlock_UNIQUE_characterId` index exists on disk → migration already ran for this store.
- No duplicate `characterId` values (5 distinct: blossom, ember, lumi, ripple, zephyr).
- Store has `ACHANGE`/`ATRANSACTION` tables (persistent history tracking — typically CloudKit-enabled).

## Decision

**D5**: Does the pre-V2 installed base have real user data that must be preserved?
- **No (pre-release, no TestFlight users with data):** Option A — `eraseDatabaseOnSchemaChange` DEBUG-gated + non-fatal RELEASE fallback. 0.5 day effort.
- **Yes (real TestFlight users):** Option B — reconstruct frozen V1 `@Model` snapshots per `VersionedSchema` + custom `MigrationStage` with `willMigrate`/`didMigrate`. 2-3 days effort.

This is the single largest effort swing in the phase and must be resolved before the planner can commit to a task breakdown.
