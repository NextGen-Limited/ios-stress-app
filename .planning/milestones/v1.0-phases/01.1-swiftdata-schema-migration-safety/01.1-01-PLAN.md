<execution_note>
CRITICAL CORRECTION TO RESEARCH.MD OPTION A: The `ModelConfiguration(...eraseDatabaseOnSchemaChange: true)` parameter named in 01.1-RESEARCH.md DOES NOT EXIST in the SwiftData SDK. Verified against `iPhoneSimulator26.2.sdk/.../SwiftData.swiftmodule/arm64-apple-ios-simulator.swiftinterface`: `ModelConfiguration` exposes only `name/schema/isStoredInMemoryOnly/allowsSave/groupContainer/cloudKitDatabase/url` — there is no erase-on-mismatch flag.

The real recovery path for "store schema does not match any declared VersionedSchema" is:
1. Catch the thrown error from `ModelContainer(for:migrationPlan:configurations:)`.
2. Delete the on-disk store at the default location: `URL.applicationSupportDirectory.appending(path: "default.store")` plus its `-wal` and `-shm` sidecars (the inspected simulator store lives at `Library/Application Support/default.store`).
3. Recreate the container with the same configuration and NO migrationPlan (a fresh store always matches the live schema).

This achieves Option A's intent (accept data loss on schema mismatch, never brick the app) using a real API. The plan's <action> bodies reflect this. If the executor finds a different `eraseOnSchemaChange`-style API in their SDK, they should prefer it — but as of iOS 26.2 it does not exist.
</execution_note>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| On-disk SwiftData store → ModelContainer | A persisted store written by an arbitrary prior build is re-opened by the current schema. Untrusted schema state crosses this boundary at launch. |
| App process → CloudKit container | The SwiftData ModelConfiguration binds to the iCloud container declared in entitlements. A mismatch between config and entitlement causes a silent sync failure or a launch fault. |

## STRIDE Threat Register (ASVS Level 1)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.1-01 | Tampering | On-disk `default.store` (prior build) | high | mitigate | Catch `loadIssueModelContainer` and recover by deleting the store + recreating the container, instead of trapping. A tampered/divergent store can never brick the app (Task 2). |
| T-01.1-02 | Denial of Service | `sharedModelContainer` initializer (line 82) | critical | mitigate | Remove `fatalError` from the RELEASE path; RELEASE falls back to a fresh, then in-memory container so launch always succeeds (Task 2). DEBUG retains `fatalError` for developer visibility. |
| T-01.1-03 | Information Disclosure | RELEASE telemetry log on recovery | low | accept | The recovery `os.Logger` line records that a store was discarded. It logs no user health data (only the SwiftData error description). Acceptable at ASVS L1; the subsystem/category tags scope it to the developer log. |
| T-01.1-04 | Tampering | CloudKit container identifier binding | medium | mitigate | Bind `cloudKitDatabase: .automatic` so the container resolves from entitlements (`iCloud.stress.ai.com`) rather than a hardcoded string; delete the orphaned `iCloud.com.stressmonitor.app` reference (Tasks 2 + 3). |
| T-01.1-03R | Repudiation | seedDefaultCharacterUnlocks after recovery | low | accept | After a recovery wipe, default CharacterUnlock rows are re-seeded deterministically; no user-authored data is silently altered. Logged via the existing recovery log line. |

No third-party package installs in this plan — the Package Legitimacy Gate does not apply (SwiftData/CloudKit/Foundation/os are system frameworks).
